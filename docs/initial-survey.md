# Taisen Hot Gimmick 한글화 — 초기 조사 (2026-09-28)

상태 표기: **확정** = 소비자/런타임으로 검증, **후보** = 정적 증거만, **미해결** = 다음 진단 필요.

## 1. 입력 (지원 리비전)

- MAME 세트 `hotgmck` "Taisen Hot Gimmick (Japan)", MAME 0.289에서 `romset hotgmck is good`. **확정**
- 하드웨어: Psikyo PS4 계열, SH-2 28.6MHz, YMF278B, 320×224 화면 2개(`lscreen`/`rscreen`), 마작 패널 입력.
- 원본 SHA1 (수정 단위 = 개별 ROM 파일, 컨테이너 없음):

| 파일 | SHA1 | 용도 |
|---|---|---|
| 1-u22.bin | 6ea7bd18bcf6224ed9b0480bb59c684f13b71d8a | 메인 프로그램 (상위 워드) |
| 2-u23.bin | bb4f57a6adffc6336fc572a4ff1f5dfc284ee4fb | 메인 프로그램 (하위 워드) |
| prog.bin | 4ce454e44da08e351a81ca4b670ff3e080dcb330 | 데이터 ROM, CPU `0x02000000` ("BGMAPTBL" 헤더) |
| 0l/0h … 3l/3h.bin | (각 4MB, `sha1sum work/src/*`) | 스프라이트 그래픽 32MB |
| snd0/snd1.bin | … | YMF278B 샘플 |

## 2. 주소 배치 (확정 — MAME 내부 메모리와 바이트 단위 일치)

- 메인 CPU 이미지 `0x000000-0x0FFFFF`: 각 32비트 = `1-u22` 워드(바이트 스왑) ‖ `2-u23` 워드(바이트 스왑). 리셋 벡터 PC=0x534, SP=0x06100000.
- `prog.bin`: 16비트 바이트 스왑 후 `0x02000000`.
- 그래픽 영역 `gfx1` 32MB: 8MB 쌍 k마다 32비트 = `kl` 워드 ‖ `kh` 워드. 스프라이트 타일 = 16×16 8bpp, 오프셋 `tnum × 256`.
- 스프라이트 RAM `0x03000000`: 스프라이트 8바이트(`y|h|x|w`, `색|flip|tnum`), 화면별 목록 `0x2C00` / `0x2E00`(끝 표시 `0x4000`).
- 메인 이미지 `0xA8100` 이후는 `0x8000` 주기로 반복됨(원본 ROM 특성). 코드가 참조하는 것은 첫 사본(`0xA77F0~`)뿐.

## 3. 런타임 텍스트 경로 (확정)

- 대사 창 문자 = 한 글자당 16×16 스프라이트 1개, 셀 16px, 빈칸 타일 `0x15582`.
- **글리프 코드 → 타일: `tnum = code + 0x1481E`** (그래픽 ROM `2l/2h`, 쌍 내부 `0x481E00~`).
- 코드 체계: JIS X 0208 압축 순서 (`work/charmap.py`).
  - `0x000-0x1A2`: 비한자 419자 (1구 2~94, 2구 1~14, 영숫자, 히라가나, 가타카나, 그리스, 키릴 대문자)
  - `0x1A3-0xD37`: 제1수준 한자 2965자
  - `0xD38-0xD63`: 선별된 제2수준 한자 44자 — **눈으로 판독한 잠정값, 검수 필요**
  - `0xD64` 이후: 폰트 끝 (그 뒤에 점수용 숫자/点符役翻 등 다른 글꼴)
- 문자열 형식: 16비트 BE 코드, `FFFE`=줄바꿈, `FFFD`=빈칸(패딩), `FFFF`=종료, 뒤에 4바이트 정렬용 `0000`.
- 참조: 32비트 절대 포인터 (출처 `0x889EC-0x89820`, 코드/데이터 혼재 영역).

### 3.1 대사 엔진 (확정 — 런타임 읽기 감시점 + 역어셈블)

- 문자열을 읽는 곳: `0x2006E` (`MOV.W @R11`), 텍스트 객체 배열 `0x0600CFA8` (0x24바이트 단위). 객체: `+0` 문자열 포인터, `+4` y, `+6` x(시작), `+0x18` 줄 간격, `+0xC` 모드(3 = 16비트 코드).
- 16비트 모드: 글자마다 x += 16. **자동 줄바꿈·열 제한·클리핑 없음** → 한 줄에 들어갈 칸 수는 창 그림이 정함.
- `FFFE`: x = 시작 x, y += 줄 간격. `FFFD`: 플래그 `0x0605CA44`가 켜져 있으면 빈칸 타일(코드 `0xD64`)을 그리고, 꺼져 있으면 x만 증가. 스프라이트는 매 프레임 다시 쓰이지 않으므로 **패딩이 이전 글자를 지움** → 번역문도 원문 줄별 칸 수만큼 패딩해야 함.
- 한 글자씩 매 프레임 출력(타자기 효과). 글꼴 기준 타일은 `@(0x2004002C)+0x408`의 서술자에서 옴(재배치 가능성 있음).
- 8비트 모드(가변폭 글꼴, 너비표 `0x306B4`/`0x305B4`)도 있으나 대사 블록은 16비트 모드. 영어 캐릭터 소개문은 ROM에 ASCII로 없음 → 그림 글자로 판단(대사 범위 밖).

### 3.2 번역 레이아웃 규칙 (채택)

- 문자열별 너비 W = 원문 줄 중 최대 칸 수(패딩 포함), 줄 수 ≤ 원문 줄 수.
- 각 줄은 원문 해당 줄 칸 수까지 `FFFD`로 채우고, 모자란 줄은 빈칸 줄로 채움.
- 원래 자리에 쓰기: 문자열 + `FFFF` + 정렬 패딩이 원래 차지하던 워드 수(capacity)를 넘으면 빌드 실패.
- 관측된 W: 12칸 대부분, 강아지 도우미 창 13~15칸, 일부 캐릭터 대사 13~17칸(패딩 없는 줄) — 후자는 창 실제 너비가 **관측값 이상일 수 있음(미확정)**.

**PoC1 (가시성, 성공)**: 미사용 한자 슬롯 8개에 한글 글리프를 쓰고 `0xAA954` 문자열을 재인코딩 → 모드 선택 화면에 "대전모드를골라요！" 표시, 크래시 없음. 스크립트 `work/poc/poc1.py`, 결과 `work/poc/snap/hotgmck/0000.png`.

## 7. 제품 빌드 경로 (채택)

```
python3 tools/khpatch.py extract --source hotgmck.zip      # translation/dialogue.json 생성·병합
python3 tools/khpatch.py build   --source hotgmck.zip      # out/hotgmck.zip + out/manifest.json
python3 -m pytest -q tests                                 # 계약 테스트
```

- 원본 13개 파일 크기·SHA1 검증(`tools/hotgmck/source.py`), 추출 시 438개 전부 무손실 왕복 확인.
- 번역 표의 보호 필드(id, 주소, 참조, 용량, 줄 칸 수, 원문 코드/텍스트)가 현재 추출과 다르면 실패.
- 한글 = KS X 1001 2,350자 고정 순서 → 원문이 쓰지 않는 한자 슬롯에 배치. 쓰인 글자만 그려 넣음. 미번역 문자열은 일본어 그대로 정상 표시.
- 모든 변경은 원본 기대 바이트가 있는 쓰기 계획으로 등록 → 겹침/기대값/최종 diff 감사 후 한 번에 적용. 실패 시 산출물 없음.
- 정책: `development`(기본, `distribution: false`) / `release`(모든 항목 `distribution_eligible` 필요).
- 검증 결과: 번역 없는 빌드 = 원본과 동일(13개 SHA1 일치). 1줄 번역 빌드 → MAME에서 "대전 모드를 골라요！" 표시 확인(`work/out_poc2/snap/hotgmck/0000.png`). 12칸 초과 줄은 빌드 실패.
- 글꼴: NanumGothic(보통) 15px, 힌팅 흑백 래스터(`fontmode "1"`). 굵게+안티앨리어싱은 받침 ㅁ이 ㅇ처럼 뭉개져(슴↔승) 폐기.

## 10. 그림 글자 (graphics text)

### 10.1 스프라이트 그림 형식 (확정 — 스냅샷과 렌더 비교)

- w×h 타일 스프라이트의 타일 번호 = `tnum + ty*w + tx` (**행 우선**). 이전 조사용 렌더러(`work/render_spr.py`)의 열 우선 가정은 틀렸음.
- 8bpp, 픽셀값 = 팔레트 뱅크 내 인덱스. 팔레트 번호 = `col × 32 + 픽셀값` (col = 스프라이트 dword1 bit24-29, 2P 화면 목록은 col에 0x20이 더해짐).
- 팔레트 RAM `0x03004000`, 항목 = BE `RRGGBB00`.

### 10.2 타이틀 로고 (적용 완료)

- 스프라이트 2개 (tnum `0x3427`, `0x34C7`, 각 10×16타일 = 160×256px, 좌우 배치, y=-32), col 0x08 (1P) / 0x28 (2P). 팔레트 원본 = 메인 ROM `0x6B210` 256색(2P 뱅크 0x500도 동일).
- 원본 로고 영역 = 시트 좌표 (23,46)-(298,173). 영역 밖은 전부 인덱스 30(배경) → 영역만 편집, 밖은 빌드가 검사로 보호.
- 한글 로고: `assets/gfx/title_logo_ko.png` (사용자 제공 2026-09-28, SHA1 7d7af4c5…; 배포 권리 근거는 사용자 확인 필요). 빌드가 알파 128 기준으로 잘라 영역에 맞게 축소·원본 팔레트 231색으로 근사 → 129타일 기록. MAME에서 1P/2P 모두 확인.

### 10.3 그림 글자 모집단과 상태 (2026-09-28, v0.8.0)

근거: 메인 ROM의 스프라이트 서식 표(8바이트 = dword0 `h-1|y|w-1|x`, dword1 `col|flag|tnum`) 중 `0x80608-0x88628` 구간 991개 항목을 렌더링(`work/catalog/static/`) + 자동 플레이 장면 311개(`work/catalog/run1/`). 코드 영역의 다른 표 후보(`0xC98`, `0x2F490`, `0x30B58` 등)는 아직 렌더링하지 않음 → **하한**.

| 묶음 | 서식 표 주소 | 개수(약) | 상태 |
